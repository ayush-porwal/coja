# coja — decisions where the design doc is silent

Each entry: the choice, and why it is the simplest option consistent with [design.md](design.md).

- **Design doc provenance.** `docs/design.md` did not exist in the working tree; two copies existed under `.delta/worktrees/*/coja/docs/`. Adopted the newest (2026-09-04 23:16) because it is the one containing the "Build order" and "Screens and UX flow" sections the build brief references.
- **Package manager / workspaces:** pnpm workspaces (`server/`, `web/`). The publishable package is `server/` (npm name `coja`); `web/` builds into `server/public/` which is included in the published files.
- **Server framework:** Hono on `@hono/node-server` (design offers Hono or Fastify; Hono has the smaller surface and streams well).
- **SQLite:** Node's built-in `node:sqlite` (no native build step for `npx coja`; requires Node ≥ 22.13, declared in `engines`).
- **Fetched PR refs are namespaced.** `git fetch origin +refs/pull/<n>/head:refs/coja/pull/<n>/head` (and the base branch tip to `refs/coja/pull/<n>/base`). Keeps objects reachable (no GC) without touching the user's branches or FETCH_HEAD semantics.
- **App-managed clones are bare.** `owner/repo` projects are cloned with `git clone --bare` into the app data dir; a bare repo has no working tree by construction. Credentials come from `gh auth git-credential` configured as the repo-local credential helper, so no token is written to disk.
- **Diff base is the merge base** (`git merge-base base head`), matching GitHub's own PR diff.
- **Thread replies follow GitHub's own rule.** We call `addPullRequestReviewThreadReply` without a pending-review id. Verified live: when the viewer has no pending review GitHub publishes the reply immediately (as a one-comment COMMENTED review); when a pending review is open GitHub attaches the reply to it, so it stays invisible until the review is submitted — exactly what github.com does. The API response reports which happened via `comment.isPending`, and the UI renders it accordingly.
- **Lint/format:** Biome (single tool for both, zero config churn). Unit tests: Vitest.
- **Versions pinned at scaffold time (2026-09-04):** TypeScript 5.9 (not 6/7, to stay on the stable line the toolchain agrees on), `@types/node` 22.x to match the `engines` floor, react-router 7, Hono 4 with `@hono/node-server` 2, Vite 8, Vitest 5, Biome 2.5, React 19.
- **Static serving is hand-rolled** (small mime map + SPA fallback) instead of `serveStatic`, so it works regardless of `process.cwd()` when launched via `npx coja`.
- **`ref=base` for blobs means the merge base**, not the base-branch tip — that is what the diff's LEFT side shows, so "read the old version" (UI and AI `read_file(base, …)`) stays consistent with the patch. The branch tip is still fetched to `refs/coja/pull/<n>/base`.
- **App-managed clones reset `credential.helper`** to empty and then `!gh auth git-credential` (as `gh auth setup-git` does) so an inherited `osxkeychain` helper cannot shadow gh with a stale credential.
- **Review-submit validation uses a bot-authored PR.** GitHub refuses `APPROVE`/`REQUEST_CHANGES` from a PR's own author, and the only account available is the user's. The fixture repo therefore carries a `workflow_dispatch` workflow that opens a PR as `github-actions[bot]` (PR #2); Approve / Request changes are validated there, Comment on PR #1.
- **"My review state" follows GitHub's opinionated-review rule** (planned fix, found in browser validation): the newest `APPROVED`/`CHANGES_REQUESTED` review wins over later `COMMENTED` ones (a published reply creates a COMMENTED review), so a reviewer who requested changes keeps that badge until they re-review — as on github.com.
- **GitHub reads are eventually consistent** after mutations (a discarded pending review's thread was still returned by the very next query). The UI re-fetches PR detail once more ~1.5 s after review mutations instead of trusting the immediate refetch.
- **AI chat routes receive a read-only `readPullRequest` function, never the `Forge`.** `app.ts` builds it from the forge; `server/src/ai/**` and `routes/chat.ts` have a static test asserting they import neither `forge/` nor `child_process`/`fs`/network modules.
- **Model output is rendered as React elements only — never raw HTML, never remote images.** Assistant markdown goes through react-markdown with `img` neutralised to inert text and links limited to http(s); the only channel an injected instruction has is the visible answer itself, and it cannot beacon data out through image loads. GitHub-rendered `bodyHTML` (PR description, comments) is the sole use of `dangerouslySetInnerHTML`, relying on GitHub's server-side sanitiser, and the served document carries a CSP as a second line of defence.
- **Request guard semantics.** Every request must carry a loopback `Host` (or one passed via `--host`); non-GET requests must be same-origin (`Sec-Fetch-Site: same-origin`/`none`, else `Origin` host must equal `Host`); `same-site` is refused because another local port is a different origin; JSON bodies must be `application/json`; `OPTIONS` is refused so cross-origin preflights never succeed. Requests with neither `Sec-Fetch-Site` nor `Origin` (curl, local tooling) are allowed by design — the guard protects against browsers, not the local user. Wildcard binds (`0.0.0.0`, `::`) are rejected at the CLI because the guard could never match them.
- **Theme architecture (UI run, 2026-09-05).** One palette id selects a *pair* of variants (light+dark, both shipped per t3code palette), and the stored preference is `{palette, appearance: system|light|dark}` — t3code's own model. Everything renders from one application step: `applyTheme` writes `--coja-*` chrome variables **and** the `--diffs-*` diff variables on `:root`; the two registered Shiki themes (`coja-light`/`coja-dark`) are `createCssVariablesTheme`-style themes whose token colours are `var(--diffs-token-…)`, so switching palette or appearance is pure CSS — no re-tokenization and no per-palette Shiki theme files. Diff row-tint *overrides* (`--diffs-bg-*-override`) are set on `:root` too; they inherit through the Pierre shadow roots and outrank the library defaults by being the first binding in the stylesheet's own `var()` fallback chains (the t3code mapping idea). The tree uses `@pierre/trees`' documented `themeToTreeStyles` with a small workbench-colour object built from the same palette. The `dark:` Tailwind variant is repinned to `[data-coja-appearance]` so the user's explicit choice beats the OS.
- **Diff token colours are coja's, not t3code's.** t3code's palettes stop at code background/foreground, so each palette carries a hand-tuned `syntax` ramp (keyword/function/string/constant/comment/punctuation in oklch) anchored on the palette's accent hue; hues collide (e.g. Grove green keywords vs. conventional green strings) are resolved per palette by rotating string/constant hues.
- **T3 Chat is renamed Mulberry.** Same palette values, new name at the user's request; the id is `mulberry` everywhere (registry, storage — a stored `t3-chat` id falls back to the default, which is Mulberry anyway).
- **Diff row fills are t3code's formulas, verbatim.** The first cut mixed changed rows in `lab` toward pre-muted palette roles, and they read as faint tints rather than bands; the user asked to just copy t3code's styles, and that was the fix — their `DIFF_SURFACE_THEME` recipes use `color-mix(in srgb, code-background N%, success/destructive)` against the *full-strength* colours, and sRGB mixing preserves the saturation that `lab` mixing loses. Row 50 %/70 % (light/dark), number gutter 35 %/60 %, word-emphasis 80 %, hover 85 %; the `light-dark()` pairs are resolved per appearance in `applyTheme`, which knows what it is painting. No dedicated fill roles in the palettes.
- **Diff colour policy per theme (and what t3code actually does).** t3code derives deletions from the palette's own `error` role (`--destructive: var(--error)`) but keeps additions on one fixed green (`--success: var(--color-emerald-500)`) for every palette; appearance contrast comes from the mix ratios, not from different colours — dark bands are 70 % background / 30 % colour, which keeps the fill dark so near-white diff text stays readable. coja copies that policy: `danger` per palette (verbatim t3code `error`), `ok` one fixed green, `code`/`codeInk` per palette, so every theme's fills differ through its own background while the anchors stay stable. The one measured failure — Mulberry light, whose code ink (0.445, t3code's own value) reached only 3.7:1 on its 50 % addition fill because green carries far more WCAG luminance than red at equal lightness — was fixed by darkening that palette's light `codeInk` to 0.36→0.32. `web/src/themes/contrast.test.ts` now computes the real fills (oklch → sRGB → CSS-spec mix → WCAG ratio and OKLab ΔL) for every palette × appearance and enforces: ink ≥ 4.5:1 on both fills, each band ≥ 1.3:1 against the code surface and ≥ 0.06 OKLab lightness away from it, context rows ≤ 0.03. Adding a palette that fails any of these fails the test suite.
- **Marking Viewed collapses the file — and every collapsed-set update is deferred past the virtualizer's render window.** Collapsing synchronously in the checkbox's own event (or, as reported, collapsing a second file via the chevron while the first collapse's async render was still in flight) throws `@pierre/diffs`' "rendered a different file than its prepared layout": the virtualizer's worker renders resolve late and claim a prepared layout that no longer matches, and React unmounts the whole screen. Three layers now: (1) the collapsed variant is a `file` item under a **distinct id** (`collapsedItemId`), so the library tears down and mounts a fresh virtualized file per state instead of re-preparing the expanded one in place — the actual race fix; (2) all collapsed-set mutations go through `scheduleCollapsed`, a double-rAF deferral that lands strictly after in-flight render cycles; (3) a `VirtualizerBoundary` around the CodeView recovers any residual throw by remounting the view (restoring scroll position), with a crash-loop fallback after three failures in 5s. Files already VIEWED at load never collapse; only the user's own check does, and the chevron can always re-expand. The collapsed set persists per PR (`coja.collapsedFiles:<projectId>/<number>`), so a reload or a visit to Overview keeps your collapsed files — consistent with the viewed state they mirror, which lives on GitHub.
- **Split-diff columns resize through a CSS variable, not React state.** The library's split grid is `grid-template-columns: 1fr 1fr` in its shadow stylesheet; DiffView injects a *static* `unsafeCSS` override that reads `var(--coja-split-left)` (a percentage) instead, and `SplitDivider` drags by writing that one variable on the diff root — a drag is pure CSS relayout with zero React re-renders, and the divider handle positions itself from the same variable. The ratio persists per user (`coja.splitLeftPct`, clamped 20-80 % so neither side collapses) and is keyboard-operable (`role=separator` values, arrows ±2 %, Shift ±5 %, Home/End to the bounds). The divider renders only in split mode.
- **Scrollbars are thin clue bars via standard properties; the tree forces its thumb visible through `unsafeCSS`.** The app sets `scrollbar-width: thin` + a 35 %-ink `scrollbar-color` on every element (with `::-webkit-scrollbar` rules for engines that need them), giving a quiet position/remainder indicator on all light-DOM scrollers (chat, overview, dialogs, diff host). The `@pierre/trees` stylesheet makes its own scrollbar thumb transparent until the tree is hovered — invisible exactly where a long file list most needs a depth clue — so Sidebar injects tree-scoped CSS via the component's documented `unsafeCSS` option forcing `--trees-scrollbar-thumb-current` to the same themed ink at all times. Test-browser caveat: the in-app browser ignores `::-webkit-scrollbar` and paints overlay thumbs only mid-scroll, so at-rest visibility was verified via computed styles; browsers that paint overlay thumbs at rest (the user's, per screenshot) show the tree bar like any other.
- **Panel widths are clamped by the viewport, not just by constants.** Asides render `width: min(<persisted>px, calc(50vw - 140px))`: on wide screens nothing changes, but below ~1000 px the CSS cap keeps ≥ ~260 px for the diff (both panels + handles) instead of letting the flex row push the main pane to zero width. Drag/keyboard resize clamps stay in JS (`PanelResizeHandle`); the CSS term only guards against window resizing.
- **Collapsed-panel badges.** The file-tree toggle shows the PR's comment-thread count while collapsed; the AI toggle shows the number of context chips waiting in the composer (lifted via `Composer.onChipsChange`). Badges hide while a panel is open — content speaks for itself.
- **File collapse rides the item shape, not the library.** `@pierre/diffs` CodeView renders a `file` item with empty contents as just its header (verified against `FileRenderer`'s empty-contents path), so collapse/expand swaps the item under the same id — no shadow-DOM hacks, and the virtual layout stays arithmetic. A jump request (tree click, AI citation) into a collapsed file expands it first and leaves the scroll nonce unhandled so the jump re-issues after the rebuild.
- **Tailwind tokens, not component CSS.** `index.css` maps the semantic vocabulary to Tailwind utilities via `@theme inline` (`bg-canvas`, `text-ink`, `border-edge`, …), so components keep utility classes while every colour resolves through the runtime `--coja-*` variables; Biome's CSS parser got `tailwindDirectives: true` for the `@theme`/`@custom-variant` at-rules.
- **ChatGPT subscription provider: implement the flow ourselves, no new dependency (2026-09-05).** The `chatgpt-oauth` npm library is excellent documentation but a wide audit surface (react/react-native/realtime/app-server/images entry points, 52 files) with a single maintainer, for roughly eighty lines of glue we can own: `server/src/codex/` implements the public Codex CLI OAuth client (`app_EMoamEEZ73f0CkXaXp7hrann`, PKCE + loopback `127.0.0.1:1455/auth/callback`, no secret) and the `chatgpt.com/backend-api/codex/responses` transport on top of the stock `@ai-sdk/openai` Responses provider we already ship — the library's own AI SDK bridge is exactly that shape (`createOpenAI({ fetch: wrapper }).responses`), so depending on it would buy nothing but audit weight. Full reasoning and the wire spec: `docs/research/chatgpt-subscription-auth.md`.
- **The Codex transport lives outside `server/src/ai/` on purpose.** The AI-layer invariant test forbids `fetch(` and network imports in `server/src/ai/**` — righty so, since the *agent tools* must not touch the network. A model transport is a different thing (every provider SDK does network), so the transport lives in `server/src/codex/` and `ai/providers.ts` imports its factory exactly the way it imports `createOpenAI`; the invariant suite stays untouched and green, and the chat handler still only sees a `LanguageModel`.
- **The transport is a body-rewriting fetch wrapper, not a new provider implementation.** The Codex backend rejects `temperature`/`max_output_tokens`/`stream_options`/… (the harness always sets `maxOutputTokens`, so this is load-bearing, not cosmetic), requires `store:false, stream:true, parallel_tool_calls:false` + a `client_version` query param, and needs `include:["reasoning.encrypted_content"]` so `store:false` tool loops keep their reasoning items (the installed `@ai-sdk/openai` round-trips `reasoningEncryptedContent` through provider options, which is what makes the echo work). Rewriting in the wrapper keeps the agent loop byte-identical across billing paths.
- **Subscription failures travel as marked message text (`[coja:chatgpt:<code>]`), not a side channel.** Stream errors reach the browser as plain strings, and `CodexError` marks itself in its constructor so the chat handler needs zero knowledge of billing paths (it stays byte-for-byte unchanged). The Setup surface strips the marker before display; the chat panel parses it to offer "Reconnect in Setup" (auth_expired) and — only when an API-key model exists — an explicit "switch for the next message" button. The switch is never automatic: no silent billing-path changes.
- **Disconnect deletes; it does not revoke.** There is no dependable public revoke endpoint for this OAuth client (PROTOCOL.md §6; Codelynx reached the same conclusion), so Disconnect removes the keychain record and in-memory state and the UI says the token expires server-side on its own / via ChatGPT settings.
- **Auth-expiry is a quarantine, not a retry loop.** A token-endpoint reply of `invalid_grant`/`invalid_token`/`invalid_request` or a bare 401/403 marks the connection auth-expired; later requests fail fast with the typed error and no network. 429/5xx/timeouts stay retryable and never quarantine. A fresh login clears the flag. Refreshes are singleflight with reload-inside-the-promise; `forceRefresh` (the 401 retry path) skips the margin re-check, a regular refresh honours it, and they join the same singleflight.
- **Models and reasoning efforts come from the backend catalog, not a curated list (2026-09-05).** `GET /backend-api/codex/models?client_version=…` is per-plan ground truth: slugs, display names, `visibility` (hidden plumbing filtered), and per-model `supported_reasoning_levels` with a `default_reasoning_level`. `ChatGptConnection.listModels()` TTL-caches it, mirrors the last good list into the settings DB (non-secret) so an outage never empties the picker, and falls back to a two-model bootstrap list before any mirror exists. The picker's reasoning-effort selector offers exactly the catalog's levels for the chosen model; the chosen effort travels in `ChatRequest`, is validated against the catalog (400 otherwise), and is injected as `reasoning: {effort}` in the transport body — deliberately not via the AI SDK's `providerOptions.openai.reasoningEffort`, whose enum predates the backend's `ultra` level. An explicit reasoning on the request always beats the injected default.

- **Custom model providers speak the two wire protocols, not vendor SDKs' newest surfaces.** The OpenAI-compatible path uses the Chat Completions protocol and the Anthropic-compatible path the Messages protocol, both pointed at a user-supplied base URL — the lowest common denominator that still covers DeepSeek, OpenRouter, Azure, proxies, and local Ollama/LM Studio. OpenAI's stateful Responses/Conversations APIs are deliberately not supported for custom providers (and not needed for the built-ins): coja keeps conversation state in its own SQLite and renders everything locally, so server-side threads would buy nothing and cost transparency + portability. ChatGPT-subscription access is the one place a Responses-shaped protocol is used, because the Codex backend speaks it. Custom provider ids are `custom-<slug-of-name>`; saving with the same slug is an intentional upsert (the edit path). Keys live in the SecretStore under that id; a blank key field on save means *keep the stored key* (it cannot be re-entered — it is never shown again), and `hasKey` travels with the config so the UI can say "key stored" without exposing material.

- **Primary navigation is the wordmark home plus a settings gear; the breadcrumb names the place.** The header reads `coja / <crumb>` as one evenly spaced run (gap 2.5 everywhere; Setup renders a "Settings" crumb automatically, the PR list passes `owner/repo`). A separate Projects button was tried and removed at the user's request — the logo already goes home, and the breadcrumb is the location indicator. The gear highlights (`bg-active` + `aria-current`) only on `/setup`. The review screen is excluded on purpose: its "← PRs" is a back link inside a task, not app navigation, and a review in progress should not offer a one-click exit to Setup in the same spot.

- **No built-in keyed providers: custom endpoints are the only key path.** Adding per-vendor Setup rows (OpenAI, Anthropic, …) does not scale and duplicated the custom-provider machinery (validation calls, model catalogs, caches). A vendor is just a custom endpoint at its official base URL — the only loss is the cheap key-validation call and discovered model lists, and hand-entering two or three model ids is the price of one uniform mechanism. The ChatGPT subscription stays separate because its value is the auth flow, not the endpoint. Vendor-side stateful surfaces (OpenAI Responses/Conversations) remain unsupported for the same reason: coja owns conversation state locally.

- **Setup's checklist uses AND/OR connector chips, not just stacked rows.** GitHub is required; the two AI sources (ChatGPT subscription, model providers) are alternatives. A small centered chip on each divider — "AND" after GitHub, "OR" between the two AI rows — makes that logic scannable without reading the copy. Purely decorative (aria-hidden); semantics stay in the text and badges.

- **Custom providers' "Fetch model list" is best-effort, never a gate.** Most compatible endpoints implement `GET {base}/models` (OpenAI, DeepSeek, OpenRouter, Z.AI, LM Studio, recent Ollama; Anthropic with `x-api-key` + version header), so Setup's form offers a one-click fetch that merges the result into the editable model chips. But proxies and older runtimes skip the route, so: the server probes through a single POST (provider id → stored key, or inline base URL + key), answers a soft 502 naming the endpoint's status with "add models by hand" instead of failing, accepts the three observed response shapes (OpenAI `{data}`, bare array, `{models}`) plus display names, caps at 64, and manual entry remains always available. The form's fetch uses the provider `id` when editing so the stored key can be reused without ever showing it.
